# 审批模块能力与边界

## 能力事实判定

能力是否可用，按以下证据优先级确认：当前版本发布清单、正式接口文档、配置后台可见项、验收记录、历史方案。低优先级材料不得覆盖高优先级证据。无法确认时使用“待确认”，不要写成“已支持”。

## 通用能力域

| 能力域 | 通用模块负责 | 业务系统负责 |
| --- | --- | --- |
| 流程定义 | 节点、连线、路由、版本、发布 | 业务场景选择和业务语义 |
| 参与人 | 按用户、角色、组织关系或规则解析 | 提供准确的业务上下文和组织数据 |
| 流程运行 | 创建实例、生成任务、推进路径、结束实例 | 决定何时发起及结果如何驱动业务单据 |
| 任务操作 | 同意、驳回、退回、撤回、转交等受控动作 | 在业务页面调用允许的动作 |
| 表单与数据 | 承载审批快照、字段权限和意见 | 维护业务主数据、校验规则和复杂交互 |
| 通知 | 按标准事件触发通知并记录结果 | 提供业务文案参数和专属触达规则 |
| 审计 | 记录定义版本、操作者、动作、时间和结果 | 保留业务侧调用、回调和单据变更日志 |
| 集成 | 提供发起、查询、操作、事件或回调契约 | 鉴权接入、幂等、重试、对账和补偿 |
| 运维 | 实例查询、异常定位、受控干预 | 业务数据修复和业务结果补偿 |

## 审批类型与流程模型

流程模型由表单和流程流转模型共同构成。流程流转模型负责节点、路由、参与人和状态推进；表单提供审批对象、摘要、字段和终端展示。

- **业务表单类**：引用现有业务系统表单和业务单据。业务系统维护主数据、页面和专属交互；审批模块保存流程快照、任务与审计。
- **自定义表单类**：新建自定义表单，并与已发布的流程流转模型及其版本绑定。表单定义、字段来源、校验、权限和摘要规则必须登记。

已有业务表单时不得为同一业务对象重复建设自定义表单。审批类型或已发布表单结构发生改变且影响历史数据、页面或实例时，单独评审迁移与兼容方案。

## 业务表单扩展与必审

摘要由文本和该业务表单内字段组合，文本不加括号、字段使用【字段名】，不得引用表单外字段。

业务表单类至少登记业务线及负责人、表单名称和标识、维护系统、摘要规则、特殊条件字段、适用范围、可确认字段、审批详情页展示字段，以及 Web、APP、H5 的展示和跳转配置。适用范围当前仅支持资产、权限组、部门、班级、点位或无需区分；其中资产和权限组可以同时选择，其他选项单选。业务表单的对应字段必须能与所选适用范围匹配，进而定位唯一、明确的流程模型。后续由配置人员在系统中配置流程模型时校验适用范围值不重复，同一个值不能出现在不同流程模型中。选择无需区分时，该表单在系统中只能创建一个流程模型；不填写取值或范围。

必审默认关闭。业务校验是流程关联模块，用于控制业务单据是否必须审批；新增业务表单审批时，研发应在所属业务线的业务校验中补充该表单。本 skill 仅输出该研发提醒，不收集或要求当前定义开关值。开启后，业务提交前必须校验业务表单已关联可用且已发布的流程模型；表单不匹配、未关联或模型不可用时，提交必须失败并返回可识别原因。记录开关、适用表单、操作人、时间和变更前后值。

## 需求归属规则

### 功能应用

满足以下条件时调用现有能力：需求可由已发布节点、路由、参与人、表单权限、任务动作或通知能力组合完成；差异主要是业务参数；不需要修改流程引擎状态或审计语义。

### 通用模块候选迭代

满足以下条件时提交模块负责人：至少两个业务场景可复用；业务差异可通过参数或扩展点隔离；需要模块统一保证权限、审计、状态、版本或任务一致性；若各业务分别实现会产生明显重复或风险。

候选不等于承诺上线。提交时附复用场景、能力缺口、期望契约、兼容性影响和验收标准。

### 业务系统实现

以下内容通常留在业务侧：业务金额或额度计算、业务资格判断、专属主数据维护、复杂表单交互、单据编号、业务结果写回、业务报表和只对单一场景有意义的页面动作。

### 禁止做法

- 绕过审批任务接口直接修改实例或任务状态
- 以共享账号、硬编码个人或前端传入任意审批人代替受控参与人解析
- 覆盖已发布定义而不产生新版本
- 让业务回调重复执行产生多次扣款、发货、授权或状态推进
- 删除或改写审计记录以“修复”流程
- 让敏感字段在非授权节点可见或可编辑

## 本 skill 的边界

流程引擎仅负责从审批页跳转到已登记的业务目标页面；目标页内如需展示或处理相关审批，由业务方自行实现页面和逻辑，不属于流程引擎模块。

本 skill 只登记和评审审批应用在上线前必须明确的业务规则、表单、数据、权限、集成和验收条件。它不产出流程图、节点设计表、节点标识、节点顺序、连线或任何实际节点配置；这些内容由上线后的配置人员在审批模块中自定义创建和维护。

## 核心建模规则

1. 流程定义、流程实例、审批任务和业务单据使用不同标识。
2. 流程实例绑定创建时的定义版本。
3. 参与人规则必须可以复现，并提供无人、多人、离职和组织变更的处理。
4. 路由条件必须声明数据来源、计算时点和默认路径。
5. 每个操作必须由模块校验权限和当前状态，前端显隐不能替代服务端控制。
6. 审批数据默认使用发起时快照；若需要读取实时数据，要声明一致性和追溯方式。
7. 回调消费方按事件标识或幂等键去重，并保留处理结果用于对账。

## 状态分层

流程实例可使用草稿、运行中、已通过、已拒绝、已撤销、已终止等业务无关状态。任务可使用待处理、已完成、已取消、已转交、已超时等状态。业务单据状态由业务系统定义，并通过明确映射与审批结果关联。

不得把“流程已通过”等同于“业务处理已成功”。审批完成后的业务执行可能失败，业务系统必须保留重试或人工补偿状态。

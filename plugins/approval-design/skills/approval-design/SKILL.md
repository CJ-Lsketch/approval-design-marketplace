# 审批设计

## 目标

把业务审批需求转换为可登记、可接入、可评审、可验收的《审批流程需求交付表》。引导用户知道需提供什么、每项为什么必要、应从哪里取得并如何填写。优先复用已发布的通用能力；识别能力缺口时，明确进入通用模块迭代还是由业务系统承担，不把业务特例写进通用内核。实际节点由上线后的配置阶段自定义创建，不属于本 skill 的输出或评审范围。

## 先读取参考资料

- 设计或评审任何审批方案时，读取 [审批模块能力与边界](references/capability-boundary.md)。
- 需要生成完整交付物时，再读取 [审批设计输出模板](references/output-template.md)。
- 需要逐项验收、纠错或做上线前检查时，再读取 [审批设计检查清单](references/review-checklist.md)。
- 需要以对话方式逐题收集业务表单接入信息时，读取 [逐项问答辅助](references/intake-assistance.md)。

## 工作流程

### 1 先说明交付方式

先告知用户：本 skill 不要求节点设计或配置。对需要关联已有业务单据的审批，按 [逐项问答辅助](references/intake-assistance.md) 收集“业务表单接入问卷”。一次只展示当前问题，不预先展示后续问题，也不先问泛化的业务场景、流程路径或节点。

每一题都必须按以下顺序进行：

1. 标注题号和问题。
2. 用一句话说明为什么需要。
3. 给出可直接复制的回答格式；必要时给出非事实性的填写示例或可选项。
4. 收到回答后复述已记录内容。信息不足时最多追问一个与本题直接相关的问题。
5. 确认、标记“待确认”或记录“不适用”后，才进入下一题。

不臆造字段标识、页面名称、接口、版本或已上线能力。用户不知道时，说明应向哪个业务角色或从哪类材料获取；若不阻塞当前问卷，记录确认人和截止时间。

关联业务单据是创建审批流程的前置条件。第 2 题必须得到具体业务表单名称；若用户没有现成业务单据或只能给出笼统类别，明确告知“请先定义业务单据，再创建审批流程”，停止问卷，不得把该项记为可跳过的待确认或继续创建流程。

对缺失信息逐项给出：

- **为什么需要**：它影响的审批类型、数据展示、权限、业务规则、集成、验收或风险。
- **如何提供**：应填写的值、可接受的材料来源、责任人或系统位置。
- **缺失处理**：是否阻塞提交；不阻塞时标为“待确认”，并写确认人和截止时间。

### 2 收集输入

先提取已有材料中的事实，再按交付表补齐影响上线的缺口。至少确认：

- 所属业务线、需关联的业务单据和触发审批的按钮
- 适用范围、摘要格式、特殊条件字段和可确认字段
- 完整字段字典：字段标识、类型、值域或单位、来源、取值时点、敏感级别、快照或实时读取方式，以及标题、摘要、确认、分支和节点权限中的用途
- 摘要规则：由文本和业务表单字段组合；文本不加括号，字段使用【字段名】；所选字段必须属于该表单
- 审批路径的业务规则、分支依据、多人处理语义和参与人规则；只记录业务要求，不转换为具体节点、连线或配置
- 参与人找不到、多人命中、离职或组织变化时的业务处理原则和权限范围
- 发起人可执行的撤回、催办、抄送、转交等操作
- 驳回、退回、撤销、超时、重复提交、人员离职等异常规则
- 上游业务系统、审批模块和下游系统之间的数据与事件交互
- 时效、审计、留痕、通知、查询和数据保留要求
- 审批详情页展示字段，以及 Web、APP、H5 的展示字段与业务详情跳转配置；流程引擎仅负责审批页跳转的目标页面，目标页内的审批展示和交互由业务方负责
- 新增业务表单审批时，提醒研发在所属业务线的业务校验中补充该表单；业务校验是控制业务单据是否必须审批的流程关联开关，不向业务方收集或要求当前定义开关值
- 是否开启必审；开启时的表单关联、可用流程校验和提交失败处理

此阶段不要求业务方预先给出节点设计表，也不由本 skill 推导节点、路径或节点配置。只确认会约束后续配置的业务规则、数据、权限和异常边界。

若缺少的信息会改变流程路径、责任人或数据权限，将其列为阻塞项，不自行补造。对不影响主路径的缺口，可以给出带假设标记的建议方案。

### 3 判断需求归属

按以下顺序分类每项需求：

1. 已发布的通用能力能够满足：归类为功能应用，给出配置或调用方式。
2. 多个业务可复用、业务语义可参数化且需要内核保证一致性：归类为通用模块候选迭代，提交模块负责人评估。
3. 只服务单一业务、依赖专属数据或页面交互：归类为业务系统实现，审批模块只承接流程职责。
4. 破坏审计、权限、状态一致性或版本可追溯性：标记为不允许，并给出合规替代方案。

不得仅凭方案名称判断能力是否上线。以模块版本发布清单、接口文档和配置后台实际能力为准；证据不足时标记为待确认。

### 4 确认配置前约束

记录后续配置必须遵守的业务规则，不输出流程图、节点标识、节点名称、节点顺序、连线或节点参数。至少明确：

- 发起、完成、拒绝、退回、撤回、撤销、终止和重新提交的业务语义
- 特殊条件字段名称；不收集条件规则、候选值或计算方式
- 多人处理所需的业务语义，例如任一人处理、全员处理、依次处理或并行处理；不映射为具体引擎节点
- 参与人解析依据，以及无人、多人、离职和组织变更时的业务兜底原则

本 skill 只收集需要用于后续分支的业务表单字段名称；具体条件规则、取值、优先级和计算方式由后续配置流程模型时确定。

### 5 定义状态与操作

分别描述流程实例状态、审批任务状态和业务对象状态，不把三者合并为一个字段。每个操作必须说明操作者、前置状态、状态变化、是否可重复、失败后的恢复方式，以及是否产生通知和审计记录。

至少覆盖提交、同意、驳回或退回、撤回、撤销、转交或委托、超时处理、重新提交和终止。业务不需要的操作应明确禁用，而不是省略。

### 6 定义集成契约

用逻辑契约描述集成，不编造实际接口地址或字段名。至少定义：

- 发起请求的业务单据标识、流程定义标识和版本、发起人、参与人上下文、表单数据、回调关联标识
- 返回的流程实例标识、当前状态和受理结果
- 事件或回调的事件标识、实例标识、业务标识、结果、发生时间、版本和幂等键
- 鉴权、租户或组织隔离、签名验签、重试、去重、超时和对账机制
- 查询详情、查询待办、取消实例和补偿处理的责任边界

### 7 执行矫正

发现问题时按严重性处理：

- 阻止：越权、无审计、路径不闭合、参与人无法解析且无兜底、回调无幂等、修改已发布定义导致在途实例语义变化。
- 警告：异常路径、超时策略、通知降级、敏感字段权限或版本迁移不完整。
- 建议：命名、表格结构、说明顺序和可读性优化。

每条问题写明位置、风险、违反的规则和可执行的修改建议。不要只给“需完善”之类的结论。

### 8 输出审批流程需求交付表

按照参考模板输出《审批流程需求交付表》。每个必填或条件必填项必须同时写明“为什么需要”和“如何提供”；已有材料中的事实写明来源，缺失项写明确认人和截止时间。

1. 业务表单接入问卷：业务线、业务单据、触发按钮、适用范围、摘要、审批详情页字段与多端配置；输出研发注意事项
2. 补充信息：字段字典、权限、异常、集成、能力依据和验收要求
3. 在交付结果末尾提醒用户将需求登记至[在线登记表](https://www.kdocs.cn/l/co5Ah0IILUqN)
4. 提醒用户在原型中贴上在线登记表截图和《审批流程需求交付表》；可选补充触发按钮和跳转页面截图
5. 待确认项、风险和责任人

只输出与当前任务相关的部分；但不得省略会影响流程正确性、权限安全或上线验收的章节。

## 设计原则

- 使用通用能力表达流程控制，业务系统保留业务规则、业务数据和业务页面。
- 不预先规定实际审批节点或其配置。上线后由配置人员依据已登记的业务约束在系统中自定义创建和维护。
- 已有业务表单时使用业务表单类；只有没有现成业务表单且通用表单可以表达时才使用自定义表单类。两类审批都必须绑定已发布的流程流转模型与版本。
- 开启必审时，业务提交前必须校验业务表单已关联可用流程；校验失败时不得先完成业务再补建审批实例。
- 发布后生成新版本；在途实例继续按创建时绑定的版本运行，除非存在经过评审的迁移方案。
- 使用角色、组织关系或规则解析参与人，避免把个人姓名固化在流程定义中。
- 把最小权限落实到字段、节点、操作和数据范围。
- 让同一请求、任务动作和回调事件具备可追踪的唯一标识和幂等处理。
- 为每条路径定义终态，为每个失败点定义重试、人工处理或补偿出口。
- 将模块能力事实、推荐设计和业务假设分开表述。
- 对话收集时一次只处理一题；用户要求“跳过”时记录为待确认，不得自行补全。

## 输出语气

使用简洁、可执行的中文。先写结论，再写依据。保留“必须”“建议”“待确认”的强度差异。不要承诺未经材料证明的能力、接口、时效或上线状态。
